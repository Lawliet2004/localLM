# Trust boundaries

The UI is trusted application code. Model text, Markdown links, tool descriptions/results, skill files and OAuth metadata are untrusted data. None of these grant process, filesystem or connector permissions.

Assets: conversation history, workspace files, service credentials, GPU/CPU resources and third-party account actions.

Controls implemented so far: parameterized SQLite operations; restrictive production CSP; Markdown without raw HTML or remote image loading; native IPC validation for runtime/generation settings; random model API key; loopback runtime; removal of inherited LLAMA_* runtime options; bounded model output and stream events; cancellable generation; child cleanup; verified downloads. Further validation remains required before release.

API providers are configured and selected explicitly. Selecting a hosted API model sends its conversation context, including supplied attachments and tool results, to the configured endpoint. Remote endpoints require HTTPS; HTTP is limited to loopback hosts, and endpoint URLs cannot contain credentials, queries or fragments. API keys use the encrypted native credential store and are never returned by provider read APIs. Connection tests request the model catalog; the separate inference test sends a small model request. Default local inference and account-subscription restrictions remain separate from custom API connections.

Saved provider keys are bound to the configured URL and API format: changing either requires an explicitly supplied replacement key. Key deletion invalidates verification while retaining the connection and chat history. Provider deletion removes its credential, clears that provider from the default for new chats, and marks existing chats as requiring another model choice. Existing chats never silently fall back to another model after deletion. Provider clients do not follow HTTP redirects with credentials. Failed credential writes restore the prior provider metadata.

Connector design: Rust MCP SDK handles protocol negotiation and sessions. HTTPS required for remote endpoints; explicit localhost HTTP permitted for local tools. Credentials are encrypted in app-data files using AES-256-GCM with connector-specific authenticated data. The random key is protected through Windows Credential Manager, Linux Secret Service or macOS Keychain. The OS store must be available/unlocked; there is no insecure plaintext fallback. Linux persistence was verified across processes using a temporary entry that was deleted afterward. Credentials are never returned by read APIs or included in prompts. OAuth uses PKCE/state validation and a bounded local callback listener. Registry/tool annotations are advisory; model-issued tools require approval unless a scoped policy permits them. Remote results are size-limited and cannot trigger local execution by themselves.

Abuse cases to test: script/HTML in model output; malformed SSE; credentials in endpoint URLs; mismatched OAuth state; expired/revoked credentials; redirects leaking headers; unbounded tool catalogs/results; model selecting unavailable tools; cancellation while awaiting approval; hostile skill archives/symlinks; workspace traversal; process escape and orphan subprocesses. These are release requirements, not claims of tests already completed.


Workspace file operations use cap-std directory capabilities. Only the explicitly selected root is opened with ambient authority; relative operations stay within that capability. Native tests exercise Windows junction escape attempts for both reading and creating files. Absolute paths, parent traversal, alternate data streams, device names, malformed arguments, binary text and oversized reads are rejected. Creation uses create_new so existing content is preserved. This filesystem boundary does not imply that future local process execution is sandboxed.

Local execution is explicitly unsandboxed and requires tool selection. Approval shows code/command, language, timeout and effective cwd. Interpreter paths are configurable absolute executable paths. The starting directory must resolve within the workspace, but commands retain normal account filesystem/network permissions. An approved Python file is rechecked against its source hash immediately before execution. Inherited environment is restricted and configured additions are validated; this cannot prevent account file/credential access. Windows Job Objects and Unix process groups provide lifecycle cleanup, not isolation. A native RAII wrapper explicitly kills the managed tree on cancellation, including Unix descendants. Optional Unix RLIMIT_AS is a per-process address-space cap. PTY output has bounded acknowledgement-based buffering. See the current [implementation evidence and limits](IMPLEMENTATION_REPORT.md).

## Conversation permission modes

The user explicitly requested Ask, automatic approval and Full access modes. Native orchestration reads a persisted conversation permission enum at turn start. Ask is the default without a remembered preference. Auto-approve permits only known built-in workspace reads/listings. Full access authorizes selected tools automatically, subject to stricter native Bash/Python “always ask” overrides. Selection/schema validation, capability-backed file operations, cleanup, cancellation, timeout and output limits remain active. Local execution is unsandboxed in every mode. The UI displays the mode even when Tools is collapsed; each audit records authorization provenance. Background children cannot bypass an approval they cannot request. Dropped approval futures clean up pending records.
